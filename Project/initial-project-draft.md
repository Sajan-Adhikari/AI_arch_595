# Initial Project Draft

## Section 1: Problem Statement

Software engineering job seekers routinely apply to dozens of postings with a single, untailored resume, even though tailoring the resume to each specific job description meaningfully improves both applicant tracking system (ATS) keyword matches and human-reviewer relevance. This project builds a tool that, given a job description and my existing resume, produces a rewritten set of resume bullets and a professional summary tailored to that specific posting: pulling forward the most relevant existing experience, rephrasing it to match the posting's language and emphasis, and flagging any skills the posting asks for that my resume doesn't currently support. Success is concrete and checkable: for a given job description, did the tool select and rephrase the right subset of my real experience, using terminology that overlaps with the posting, without inventing anything I haven't actually done?

This matters because tailoring is high-leverage but doesn't scale by hand. Rewriting a resume well for one posting takes real time and attention; most people either send the same generic resume everywhere (lower response rate) or tailor only a handful of applications they care most about. For a software engineer running a broad job search, this is the single most repetitive, most mechanical, and most neglected part of the process.

It's an AI engineering problem rather than a scripting problem because the core operation is semantic matching and constrained generation, not exact string matching. A job description asking for "experience building scalable backend services" should match a resume bullet about "built a distributed job queue handling 10k requests/sec" even though they share almost no words. A keyword search or template-fill script can't make that connection or rewrite prose to fit a new context; a language model that can read both documents, judge relevance, and generate constrained rewrites can.

## Section 2: Target Users

Right now, the target user is just me: a software engineering job seeker in the middle of an active search, with a job posting open in one tab and my resume open in another, deciding whether it's worth the twenty minutes it would take to tailor it by hand before applying. That's the moment this tool needs to fit into.

What would make me use it a second time is a combination of speed and trustworthiness: the output has to be meaningfully better, or at least no worse, than what I'd write myself in a few minutes, and it has to arrive fast enough that tailoring stops feeling like a tax on applying. What would make me abandon it is any sign of fabrication — a bullet that implies I used a technology or led a project I didn't — since a resume is the one document where being caught overstating something is worse than not applying at all. A close second failure mode is generic, obviously AI-written phrasing that a human reviewer would recognize and discount.

## Section 3: Candidate Approach

I think this needs retrieval-augmented generation rather than a pure prompting approach or an agent. The resume is the source of truth, and the job description is the query: the system should retrieve the most relevant pieces of my actual experience conditioned on the posting, then use a prompted generation step to reorder and rephrase only that retrieved content to match the posting's language, explicitly constrained against introducing claims that aren't grounded in the source material. I don't think this needs agentic behavior — there's no multi-step task requiring the model to take actions in an environment, decide what tool to call next, or revise a plan; it's closer to a single retrieve-then-generate pass. I also don't think finetuning is the right call here: I have one resume, not a large corpus of my own writing, which is nowhere near enough data to finetune on, and a well-constrained prompting/RAG combination should be able to handle a rewriting task like this.

For models, I'm leaning toward starting with a hosted frontier model (Claude or a comparable GPT-family model) rather than something I'd run locally, since this is low-volume, single-user usage where cost and latency don't matter much, and capability at faithfully constrained rewriting matters more than raw efficiency. I'd like to compare that against a smaller/cheaper model to see whether quality holds up, since that comparison seems like a natural and interesting part of the evaluation.For models, cost and hardware are as much a factor here as capability. My laptop has 8GB of RAM, which rules out running anything but small, heavily quantized open models locally — realistically something in the 1B–3B parameter range (for example Llama 3.2 3B or Phi-3-mini, quantized to 4-bit and run through something like Ollama or llama.cpp), which fits in roughly 2–4GB of memory.

The hardest part, I think, is retrieval quality on a corpus of exactly one document. Most RAG examples assume a large collection to retrieve across; here, the "corpus" is a single resume, so the retriever needs something more granular than whole-document matching. My current plan is to pre-chunk the resume at the bullet level — treating each responsibility or achievement as its own retrievable unit — so the system has enough granularity to select and drop bullets intelligently rather than just returning the whole resume back. Guarding against fabrication during the rewrite step is the other hard part, and I expect that to take real iteration.

This idea builds on my Week 1 direction of a tool for my own software engineering job search. What's changed is the scope: I've narrowed a broad "job search co-pilot" concept down to one well-defined capability, job-description-aware resume tailoring, specifically because it has a clear definition of correct behavior (faithful to my real resume, relevant to the posting) that I can actually evaluate without needing a large labeled dataset.

## Section 4: First-Draft Evaluation Plan

I plan to measure two things directly and one thing more subjectively. First, faithfulness: whether every generated bullet is grounded in something actually present in my source resume, with no invented skills, technologies, or claims. This is checkable with a simple automated pass (do the generated bullets introduce terms absent from the source resume) backed up by my own manual read of each output, since I'm the only person who can say for certain whether a claim is true. Second, relevance: what fraction of a job description's key skill and requirement terms are reflected in the tailored output compared to my untailored baseline resume, which is a rough but concrete proxy for "did this actually respond to the posting."

I don't have an existing dataset for this, since it's inherently about matching my resume to postings I personally care about, so I'll build a small test set myself: roughly 10 to 15 real software engineering job postings I'm actually applying to during the term, run against my one resume. For each, I'll score the output on faithfulness (pass/fail per bullet) and on a simple 1–5 usability rubric — would I submit this bullet as-is, with minor edits, or not at all.

I'd consider this a success if faithfulness holds at or near 100% (any fabrication is a hard failure for this use case), and if a clear majority of generated bullets score "usable as-is or with minor edits" across my test postings, with measurably higher keyword overlap than my baseline resume. The thing I expect to be hardest to measure, and can't really solve within a term, is the outcome that actually matters: whether tailored applications get more callbacks than untailored ones. That requires real applications, weeks of waiting, and is confounded by the job market, company, and timing in ways a single-term project can't isolate, so this evaluation plan can only proxy that outcome rather than measure it directly.
